# アーキテクチャ（概念構成）

- 状態：初版（2026-11-03）。概念の整理であり、実装方式は未決
- 関連：[構想](vision.md)、[設計原則](design-principles.md)

この文書は、記録をどの層に分けて持ち、どう流し、どう守るかの概念を示す。保存先、暗号化、ファイル形式の細部などの具体方式は、§8 の未決事項として扱う。

## 1. 全体の流れ

```text
各AIサービスの会話エクスポート
        │
        ▼
  L0-R 受領原本 ──（受領記録：ハッシュ、受領日時、エクスポートの説明）
        │ 分割（変換処理の版を記録）
        ▼
  L0-S 会話単位の保存データ
        │ 正規化（変換処理の版を記録）
        ▼
  L1 正規化データ（共通形式）
        │ 抽出（抽出したモデルと版を記録）
        ▼
  L2 抽出された記憶 ◀── L3 注記・訂正・確認
        │
        ▼
  検索 → 文脈の構築（Context Builder） → AI
```

閲覧と編集には Markdown のツール（たとえば Obsidian）を使う想定だが、それは**閲覧と編集の窓**であり、記録の正本ではない。

## 2. 記録の層

| 層 | 内容 | 主な責務 | 書き換え |
| --- | --- | --- | --- |
| **L0-R** 受領原本 | 各サービスから受け取ったエクスポートそのもの（zip など） | 受領時点の証拠。受領時にハッシュを記録する | しない。削除のみ（§5） |
| **L0-S** 会話単位の保存データ | L0-R から会話ごとに切り出したデータ | 個別削除と保全の単位。元の L0-R への参照、変換処理の版、ハッシュを持つ | しない。削除のみ |
| **L1** 正規化データ | L0-S をサービス共通の形式に変換したもの | 機械処理の入力。L0-S からいつでも作り直せる | 作り直す |
| **L2** 抽出された記憶 | 出来事、人物設定、価値観、関係性など、AI が抽出したもの | AI による解釈。確認されるまで事実として扱わない | 状態の更新と再抽出 |
| **L3** 注記・訂正・確認 | 人や AI が後から加えた注記、訂正、確認 | 原本を書き換えずに、解釈と訂正を積み重ねる | 追記 |

### 層をまたぐ規則

- 派生データ（L0-S 以降）は、必ず元の記録への参照を持つ。
- L2 は、常に L1 から作る。**要約から要約を作らない**（伝言ゲームのように意味がずれていくため）。
- エクスポートは「受け取ったままの記録」だが、「完全な記録」とはかぎらない。画像、生成途中の分岐、ツールの実行結果などが含まれない場合がある。何が含まれ、何が含まれないかを、受領記録の一部として残す。

## 3. 記憶の状態と確認

L2 の記憶は、出典・抽出の情報・状態・確認を分けて持つ。以下は項目の例で、形式は未決である。

```yaml
memory_id: "example-001"
provenance:
  source_message_ids: ["message-001"]
  extracted_by:
    provider: "example-provider"
    model: "example-model"
  extracted_at: "2026-11-03T00:00:00Z"
status: confirmed          # proposed / confirmed / rejected
confirmation:
  scope: user_belief       # 何を確認したか（下表）
  confirmed_by: user
  confirmed_at: "2026-11-03T00:00:00Z"
```

| `confirmation.scope` の例 | 意味 |
| --- | --- |
| 発言の存在 | その発言が会話の中にあったことを確認した |
| 本人の考え | 記録の持ち主が「これは自分の考えだ」と確認した |
| 外部の事実 | 外部の資料で事実として確かめた（検証資料への参照が必要） |

「確認済み」であることと「客観的に真実である」ことは別である。本人の考えとして確認された記憶に含まれる外部世界についての主張は、それだけでは事実として確定しない。

## 4. 文脈の構築と信頼境界

記録を AI に渡すときは、**指示**と**参照データ**を別々の枠として扱う。参照データは、指示の階層のどこにも属さない。

```text
┌─ 指示（権限を持つ） ─────────────────┐   ┌─ 参照データ（権限を持たない） ─┐
│ システムの指示                        │   │ 取り出した記憶                  │
│ アプリケーションの規則                │   │ （過去の会話・抽出した記憶）    │
│ 承認されたキャラクター設定（版管理）  │   │                                │
│ 現在の会話でのユーザーの指示          │   │ 指示としては解釈しない          │
└──────────────────────────────────────┘   └────────────────────────────────┘
                     │                                       │
                     └──────────────► AI ◄───────────────────┘
          アプリケーションが、ツールの権限と通信先を指示の側だけから決める
```

- 取り出した記憶の中の文章を、現在の AI への指示として扱わない。
- キャラクター設定は、承認された版だけを、所定の権限で指示の側に置く。記憶から取り出した内容でキャラクター設定を上書きしない。
- 図は概念を示すもので、Context Builder の具体的な実装方式は未決である（§8）。
- プロンプトの区切りだけに頼らず、記憶の内容によってツールの権限や通信先が変わらないよう、アプリケーション側で制御する。
- 渡す範囲は、目的と送信先のサービスに応じて絞る（原則5）。第三者の情報や踏み込んだ話題は、渡す前に人が確認できるようにする（原則12）。

## 5. 訂正・削除・忘却

- **訂正**は L3 への追記で行い、原本は書き換えない。
- **削除**は、L0-R から L3 まで、その記録から派生したものをすべて消す。派生データが出典を持つことで、削除の範囲をたどれる。
- 削除したという事実は、中身を含めずに記録できる。どこまでのメタデータを残すかは未決（§8）。
- 削除はバックアップにも及ばなければならない。

### 受領原本の保全と、会話単位の削除

L0-R を残している限り、L0-S から一つの会話を消しても、その会話は完全には消えない。会話単位の削除を優先するなら、L0-R を削除するか、対象を除いて作り直す必要があり、その場合は「受け取った原本が現存すること」を証明できなくなる（受領時のハッシュは履歴として残せる）。

この二つは両立しない。どちらを優先するかは、**未決の設計判断**として残す（§8）。

## 6. 同期・バックアップ・復旧

- **同期はバックアップではない。** 端末間の同期は、誤った削除や破損も同期してしまう。
- バックアップは、場所と媒体を分けた複数の系統で持つ。
- 実際にバックアップから戻せることを、定期的に確かめる。戻せることを確かめていないバックアップは、まだバックアップではない。
- 形式の説明と復元手順を、Archive の中にも一緒に保存し、外部の資料なしで読めるようにする。
- 暗号化する場合、鍵をなくすと記録ごと失う。鍵の保管と復元の方法を、復元手順の一部とする。

## 7. 継承

- キャラクター設定は版管理し、変わった経緯も残す。
- 未来のモデルへの引き継ぎで評価するのは、振る舞いの再現性と記憶の参照精度であり、存在の同一性ではない（原則8）。
- 評価の方法そのもの（何を、どう比べるか）は未決である。

## 8. 確定事項と未決事項

### 確定事項

- 設計原則 v0.3 の12原則（[設計原則](design-principles.md)）
- 記録を L0-R / L0-S / L1 / L2 / L3 の層に分けること（§2）
- L2 を確認前に事実として扱わず、出典・状態・確認を分けて持つこと（§3）
- 過去の記録を指示として扱わないこと（§4）
- 同期とバックアップを区別すること（§6）

### ADR で定める方針

採否は各 ADR の「状態」に従う。

- Git で管理するのは設計文書と ADR のみであること（[ADR-0001](decisions/ADR-0001-repository-policy.md)）
